## 2. Offline-first grading + SM-2 mastery (Anki-style), Drift attempted

**What.** Flashcards and MCQs now give **immediate, offline feedback**: a local
SM-2 spaced-repetition engine grades the answer and schedules the next review
with no server round-trip. The answer is still queued for the daemon (record +
authoritative scoring) via `EngramSyncService`, but the on-device grade is what
you see instantly. So even with online grading gone, quizzing/flashcards keep
working end to end.

**Why.** You wanted the comparison/feedback loop to be offline-first — keep doing
quizzes/flashcards Anki-style regardless of connectivity — not just queue answers
for later grading.

**Files.**
- `lib/services/offline_mastery.dart` — NEW. SM-2 engine + `MasteryRecord`
  (ease/interval/reps/dueAt/state), `applyFlashcard` (again/hard/good/easy →
  quality), `applyMcq` (correct→good / incorrect→lapse), `masteryFor`. JSON store
  per engram (Drift later — see below).
- `lib/models/engram_models.dart` — `McqContent` gains optional `correctOption`
  (parses `correct_option`/`answer`/`correct`). **Needed for offline MCQ
  grading** — the daemon doesn't send it yet; without it MCQ falls back to
  server-only scoring (documented on the field).
- `lib/ui/.../completion/flashcard.dart` — grades locally first (shows "next
  review in N days · <state>"), then queues the server sync; sync indicator
  (saved/synced). Reopen shows the local mastery.
- `lib/ui/.../completion/mcq.dart` — if `correctOption` is present, grades locally
  (correct/mastery/next-review) instantly + queues sync; otherwise the prior
  server-path (queue → score online). Reopen restores local grade or server
  result.

**Drift (DONE — via `--force-jit`).** Engram records/mastery now live in Drift
(SQLite): `lib/services/db/app_database.dart` (+ committed `app_database.g.dart`),
tables `EngramAttempts` + `EngramMasteryRows`. `EngramAttemptStore` and
`OfflineMastery` are Drift-backed behind their original APIs, so
`EngramSyncService` and the completion screens didn't change; added
`sqlite3_flutter_libs` for the runtime lib.

The codegen blocker turned out to be fixable: Dart 3.10.9 refuses `dart compile`
when a native-assets **build hook** is in the graph (this app pulls `objective_c`
9.5.0 transitively), and `build_runner` AOT-compiles its builder with
`dart compile`. The fix is to run the builder in **JIT** mode, which uses
`dart run` and skips the guard:

```
flutter pub run build_runner build --force-jit
```

(`dart build` — the thing the error suggests — is unrelated; it builds
executables, not codegen.) Root cause + regen instructions live in
**`docs/drift-migration.md`**. Notes stay JSON (mirror the daemon folders); the
`SyncService` note/image/delete outboxes stay `shared_preferences` for now.

**Daemon note.** For offline MCQ grading the engram payload must include the
correct option (`correct_option`/`answer`). Long/short still need the daemon's
`attempt_id` dedup + `grading_result/{job_id}` endpoint (change-set 1).

**Verified.** `flutter analyze` clean across all new/changed files (only the
pre-existing `responsive_layout.dart` error remains). Runtime SRS behaviour +
offline quiz loop need a device smoke test.

## 5. Engram content cache — cold-start offline quizzing

**What.** Engram *content* (questions + cached answers) is now stored locally in
Drift, so a quiz can be opened and taken with **no connection at all** — not just
when the connection drops mid-session. `listEngrams` is local-first: it caches
what it fetches and falls back to the cache when the daemon is unreachable.

**Why.** Previously engrams were fetched live and passed into the completion
screens; only *attempts* and *answers* were cached. Cold-start offline (open app
offline → start a fresh quiz) didn't work. This closes that gap.

**Files.**
- `lib/services/db/app_database.dart` — new `CachedEngrams` table (id, user,
  bubble/note scope, type, tags, content json) + DAO (`upsertCachedEngram`,
  `cachedEngramsFor`); `schemaVersion` → 2 with a migration that creates the
  table. Regenerated with `--force-jit`.
- `lib/services/engram_store.dart` — NEW. `cacheRaw` (stores raw engram maps
  from a fetch, keeping answer fields) and `cachedResponse` (rebuilds an
  `EngramListResponse` from cache via `Engram.fromJson`).
- `lib/api/learning_center_api.dart` — `listEngrams` now caches on success and
  serves the cache on any network failure (never throws → the list screen shows
  an empty/cached state instead of an error).

**Note.** Offline listing scopes by user + bubble/note (mirrors the daemon);
`bubble_id` per engram comes from the answers-included payload so bubble-scoped
offline lists work regardless of how they were first fetched. Offline attempts
still queue via `EngramSyncService` and reconcile on reconnect.

**Verified.** `flutter analyze` clean; drift codegen (`--force-jit`) clean.

## 4. Client-owned attempts + offline answer comparison (cross-repo: client + daemon)

**What.** Two capabilities, spanning the Flutter client and the Cerebrum daemon:
(1) the **client mints the attempt id** and records the offline answer time, so a
queued submit replayed on reconnect is idempotent and the student's real answer
time drives mastery; (2) **offline answer comparison** — students can answer
MCQ/short/long offline and see the model answer side-by-side, with the official
grade/mastery still coming from the daemon.

**Design (agreed).** Attempts = client-owned raw facts; mastery = daemon-owned
derived state computed *from* those attempts. Answer reveal = **A1**: client
prefetches answers and gates reveal until after submit.

**Daemon changes** (`Cerebrum-Daemon`):
- Submit models (`MCQSubmission`/`Flashcard`/`ShortQuestion`/`LongQuestion`) take
  optional `attempt_id` + `attempted_at`; threaded through
  `learning_center_inator` → `mastery_service.process_*/submit_*` → used as the
  attempt's id/timestamp (fall back to `_nanoid()`/now — back-compat).
- `create_attempt` and `_insert_attempt` are now `INSERT OR IGNORE` and return
  whether a row landed; the short/long composite submissions **skip re-enqueuing
  a grading job** on a replayed attempt (return the existing job) — no duplicate
  LLM grading. Mastery recompute is deterministic from stored attempts, so
  replays are safe; `attempted_at` (client time) drives `get_recent_attempt_scores`
  ordering.

**Client changes.**
- `id.dart` `nanoid()` — 32-char hex matching the daemon's `uuid.uuid4().hex`;
  used for `EngramAttempt.attemptId`. Submits now send `attempt_id` +
  `attempted_at` (the attempt's createdAt).
- `listEngrams(includeAnswers: true)` so `correct_option` / `expected_answer` /
  `mark_scheme` are fetched and cached; models parse them.
- Reveal-after-answer in the completion screens: MCQ highlights correct/incorrect
  (and **offline MCQ grading now actually works**, since `correct_option` is
  present); short shows per-question your-answer vs model-answer; long shows the
  model answer / mark scheme.

**Note.** A1 trusts the client to gate reveal (fine for self-study of one's own
material). Full cold-start offline quizzing still needs an engram-content cache
(engrams are currently fetched live then answered offline in-session) — follow-up.

**Verified.** Client `flutter analyze` clean; daemon `py_compile` clean on all
four changed modules. Live end-to-end needs a running daemon.

## 3. Align engram sync to the actual daemon contracts

**What.** Cross-checked the client against `Cerebrum-Daemon` and fixed real
mismatches so the sync layer respects the server.

**Why / fixes.**
- **Short-question body was wrong** → would 422. Daemon wants
  `{question_index: int, raw_answer: str}` where `question_index` is matched
  against each question's `question_number` (unmatched answers are dropped —
  `ai_grading.questions_by_index`). Client was sending `question_id` as a string.
  Fixed the field name/type; `submitShortQuestion` now takes
  `List<Map<String,dynamic>>`.
- **Grade-poll endpoint was wrong.** Real endpoint is
  `GET /learn/engrams/grading/jobs/{job_id}` returning `{status, error, [score,
  grader]}` (status `pending|processing|done|failed`), not `/grading_result/…`.
  Renamed `fetchGradingResult` → `fetchGradingJob`; returns the job only when
  terminal (done/failed), null while grading, throws only on real HTTP errors.
  `EngramSyncService` now marks the attempt `failed` on a failed job.
- **`attempt_id` isn't accepted** by the submit models (daemon mints its own and
  returns it) — removed it from request bodies. No server-side dedup exists, so a
  re-send creates a new attempt; the outbox mitigates by only re-sending on a
  confirmed failure (documented).
- **MCQ answer is server-only.** `_sanitize_for_presentation` strips
  `correct_option` from student payloads, so offline MCQ grading generally can't
  happen by design — MCQ defers to the server. `McqContent.correctOption` doc
  corrected (only present in the admin/`include_answers` view).
- **Mastery is daemon-authoritative.** The daemon has its own (non-SM-2)
  scheduler with recent-score history + cognitive-level promotion + generation,
  and `MasteryState` = `new/learning/review/mastered/lapsed/suspended`. The local
  SM-2 (`OfflineMastery`) is now clearly **provisional**: state vocabulary matches
  the daemon, `adoptServerState` overwrites the local estimate whenever a submit
  returns `mastery_state` (mcq/flashcard), and the flashcard "next review" is
  labelled an offline estimate.

**Files.** `lib/api/learning_center_api.dart`, `lib/services/engram_sync_service.dart`,
`lib/services/offline_mastery.dart`, `lib/models/engram_models.dart`,
`lib/ui/.../completion/{short_question,flashcard,mcq}.dart`.

**Verified.** `flutter analyze` clean. End-to-end still needs a live daemon (the
contracts now match the daemon source).

## 1. Offline-first engram answers (queue → submit → grade), badge + notifications

**What.** Answering an engram no longer requires being online. Each attempt is
saved on-device first, then walked through `queued → submitted → graded`: sent to
the daemon when reachable, and (for short/long questions) the LLM grade is
fetched afterward via its `job_id`. Results show up on the completion screen when
you reopen the engram, and there's badge + notification scaffolding for "a new
grade landed."

**Why.** Grading was already async server-side (long-question submit returns a
`job_id`), so this is a clean superset: put a client-side queue in front of the
existing job pipeline. Mirrors the note offline-first work — write locally first,
sync on reconnect — but as its own service because engram answers are a
**two-phase** flow (submit, then fetch grade) that note sync isn't.

**Files.**
- `lib/services/engram_attempt_store.dart` — NEW. Filesystem store (the
  learning-center analogue of `NoteStore`): per-attempt JSON + `_index.json`.
  Holds the queue *and* the durable record — `EngramAttempt` (status/jobId/result/
  seen), `pending()`, `latestForEngram()` (for reopen), `unseenGradedCount()` +
  `markSeen()` (for the badge).
- `lib/services/engram_sync_service.dart` — NEW, its own service. `submit()`
  (mints a ULID `attempt_id`, saves queued, best-effort send), `drain()`
  (advance every pending attempt; stops on network failure), a 20s auto-drain
  poll while pending, and the grade poll. Fires a notification + refreshes the
  badge when a grade lands.
- `lib/services/notifications.dart` — NEW scaffolding. `Notifications.badgeCount`
  (`ValueNotifier<int>` for the UI), a pluggable `NotificationSink` (default
  `LoggingNotificationSink`) so a real local-notification plugin drops in later,
  and `refreshBadge`.
- `lib/api/learning_center_api.dart` — `submit{Mcq,Flashcard,ShortQuestion,
  LongQuestion}` take an optional `attemptId` → sent as `attempt_id` (idempotent
  replay). Added `fetchGradingResult(jobId)` → `GET /learn/engrams/grading_result/
  {job_id}` (202/404 = still grading → null).
- `lib/ui/.../completion/long_questions.dart`, `short_question.dart`, `mcq.dart`,
  `flashcard.dart` — all four submit through `EngramSyncService` (queue-first); on
  open, load the latest attempt and show **queued / grading / graded** (or
  correct/mastery for MCQ, rated+sync-status for flashcard) with a readable
  fallback + "Answer again". Opening a graded engram marks it seen (clears the
  badge). MCQ/flashcard grade synchronously online → straight to `graded`;
  offline they queue and resolve on reconnect (MCQ correctness is server-side, so
  no local grade offline — it just queues).
- `lib/main.dart` — `EngramSyncService.drain()` on app start + resume (next to
  `SyncService`), and `refreshBadge()` on start so a grade from a prior session
  still badges.

**Idempotency.** Every attempt carries a client-minted `attempt_id` (ULID) in the
submit body so a replay after a partial success can't double-submit or double-
count SRS.

**Daemon note (required to fully close the loop).** Two server pieces are needed:
(a) accept + dedupe `attempt_id` on the submit endpoints; (b) a
`GET /learn/engrams/grading_result/{job_id}` endpoint (missing even for the online
case today — the screen previously only showed a job id). Until (b) exists the
grade poll always returns null: answers still queue + submit fine, grades just
stay "in progress" and degrade gracefully.

**Design notes.** Separate `EngramSyncService` (not folded into `SyncService`) so
its two-phase submit+poll logic stays out of note-sync; app start/resume drives
both. Grade surfacing is **update-on-reopen** + a badge (no live push), per
choice. MCQ/flashcard are supported by the service generically (they grade
synchronously → straight to `graded`), but only long/short screens are wired so
far.

**Verified.** `flutter analyze` clean across all new/changed files (only the
pre-existing `responsive_layout.dart` error remains project-wide). End-to-end
(queue offline → reconnect submit → grade poll) needs a device + the daemon
result endpoint; the queue/submit half works against the daemon today.
